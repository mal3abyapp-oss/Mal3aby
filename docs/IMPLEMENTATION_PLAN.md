> **⚠️ GIT POLICY: LOCAL ONLY.** Every phase below ends with a **local** stable commit and a stop. `git push`, GitHub repository creation, GitHub Actions, and any Cloudflare/production-Supabase action are blocked until a separate, explicit go-ahead — see [PROJECT_RULES.md](PROJECT_RULES.md) rule 5b. Phases 17 and 18 describe the target end-state and remain in the plan for sequencing purposes, but are **not** to be executed under the current authorization.

22 phases (19 numbered 0–18 + 3b + 3c + 3d). RLS and multi-tenancy land before any domain data (retrofitting tenant isolation onto a live model is the most expensive rebuild this project could suffer). Platform Billing (3b/3c) lands immediately after Staff/Permissions — it depends only on `clubs` and Platform Owner role/permission plumbing from Phases 2-3, and every later phase's access-gating (`auth.club_write_allowed()`) depends on 3b's `get_club_platform_access()` existing first. 3c (the full console UI) is split out from 3b (data model) so each phase stays a manageable, single-sitting unit of work per [PROJECT_RULES.md](PROJECT_RULES.md) rule 14's phase discipline. **3d (public site + signup + trial) follows immediately after 3c** rather than waiting until the rest of the product is built — the brief is explicit that this should not wait for project end, and 3d only needs Auth (Phase 2) + the trial/subscription machinery (3b) + a place to send a new club owner (Phase 1's `AppLayout` shell, even mostly empty) to be functionally complete end-to-end. Booking lands before Academy so Academy can reuse the same billing/QR/RPC pattern instead of inventing a parallel one. Dashboards/reports are woven into the phase that produces their data rather than one late catch-all phase. See [DECISIONS.md](DECISIONS.md) for why this reorders the original brief's Section 89 sequence.

No phase begins until the previous phase's exit gate passes — which now means both its **Functional Gate and Security Gate**, not functional alone. "Done" for any feature follows [PROJECT_RULES.md](PROJECT_RULES.md) rule 9 (Definition of Done) in addition to the phase-specific acceptance criteria below. **Phase discipline (see [PROJECT_RULES.md](PROJECT_RULES.md) rule 14): at the end of every phase — run tests, run build, review migrations, review RLS, review `git diff`, update docs, update `PROJECT_STATE.md`, local stable commit, stop and report. Do not auto-continue into the next phase.**

**Phase template (restated per phase where it applies):** Objective · Scope · Database · Frontend · Business Logic · Security · Tests · Responsive QA · Documentation · **Functional Gate** · **Security Gate**. Every phase below already follows this shape under its existing headings (Goal/Database work/Frontend work/Security work/Tests/Exit gate) — the Security Gate is the explicit checklist from [SECURITY_ANTI_FRAUD.md](SECURITY_ANTI_FRAUD.md#security-gate-checklist-applied-per-phase-where-applicable), applied to whatever that phase touches.

### Phase 3b — Platform Billing Data Model + Access Control
**Goal:** the data model and access-derivation logic for Mala3by billing clubs, structurally separate from a club's own customer billing (see [DECISIONS.md ADR-028](DECISIONS.md#adr-028--platform-billing-is-a-structurally-separate-domain-from-club-billing)). This must exist before later phases' write-gating depends on it. **Note: `clubs.status` gets no new value here** — it stays `active`/`suspended`/`closed`, unrelated to this phase's subscription concept (see [DECISIONS.md ADR-027](DECISIONS.md#adr-027--clubsstatus-and-platform-subscription-status-are-fully-independent-grace_period-is-never-a-club-status)).
**Database work:**
- `clubs.status` enum finalized as `active` | `suspended` | `closed` (no `grace_period`).
- `platform_settings` singleton (`default_trial_days` default `7`, `default_grace_period_days` default `7`) — see [DECISIONS.md ADR-037](DECISIONS.md#adr-037--trial-length-is-a-platform-setting-not-hardcoded).
- `platform_plans` seeded with four rows: Monthly (`month × 1`), Quarterly (`month × 3`), Semi-Annual (`month × 6`), Annual (`year × 1`) — see [DECISIONS.md ADR-029](DECISIONS.md#adr-029--platform-plan-supports-real-billing-intervals-monthly-quarterly-semi-annual-annual). Includes `is_public`/`display_order`/`name_ar`/`description_ar`/`discount_label`/`features_summary` from day one (used by Phase 3d's public site) — see [DECISIONS.md ADR-040](DECISIONS.md#adr-040--public-plan-data-is-exposed-through-a-restricted-viewrpc-never-the-raw-platform_plans-table).
- `public_plans` view (safe public column subset, `is_public = true` only) — see ADR-040.
- `platform_subscriptions` as a period-based table (one row per billing cycle, snapshot columns including `subscription_kind`, `previous_subscription_id`, exclusion constraint preventing overlap while allowing adjacent renewals, unique partial index enforcing at most one non-cancelled trial per club — see [DECISIONS.md ADR-030](DECISIONS.md#adr-030--platform-plan-pricing-is-snapshotted-onto-each-subscription-period)/[ADR-031](DECISIONS.md#adr-031--renewal-creates-a-new-subscription-period-row-periods-are-never-mutatedextended-in-place)/[ADR-032](DECISIONS.md#adr-032--overlapping-subscription-periods-are-prevented-adjacent-renewal-periods-are-allowed)/[ADR-038](DECISIONS.md#adr-038--trial-is-a-subscription_kind-not-a-new-concept-trial-expiry-defaults-to-blocked-not-automatic-conversion)/[ADR-039](DECISIONS.md#adr-039--trial-belongs-to-the-club-not-the-user-one-trial-per-club-ever)). **`subscription_kind` (`trial`/`paid`/`complimentary`) built in from the start** — trial is not retrofitted later, it's part of this table's initial design.
- `platform_invoices`, `platform_payments` (with reversal columns, not hard delete).
- `get_club_platform_access(club_id)` central function (`full`/`grace`/`blocked`) and the `auth.club_write_allowed()` wrapper — see [ARCHITECTURE.md](ARCHITECTURE.md#platform-access-strategy) and [DECISIONS.md ADR-033](DECISIONS.md#adr-033--platform-access-is-full--grace--blocked-derived-by-one-centralized-db-function). Confirmed to handle trial periods (`grace_period_days_snapshot = 0`) with no special-case branch — a zero-width grace window falls out of the same derivation used for paid periods.
- RPCs: `create_platform_subscription` (activate/start trial — creates the first period), `renew_platform_subscription` (creates a new period with `previous_subscription_id` set, re-snapshotting current plan terms or an explicitly chosen new plan), `change_platform_plan` (ends current period early via cancellation + creates a new period on the new plan — recorded as a plan change, not silently overwritten), `cancel_platform_subscription` (sets `lifecycle_status = 'cancelled'`, requires reason), `record_platform_payment`, `reverse_platform_payment`, `extend_grace_period` (per-subscription override of `grace_period_days_snapshot`).
- `contact_requests` table (anonymous insert-only, Platform-Owner select/update) — built here since it shares the "public-safe write surface" concern with `public_plans`, even though it's used starting Phase 3d.
- Restricted view for Club Owner's own-club summary (see [DECISIONS.md ADR-035](DECISIONS.md#adr-035--club-owner-subscription-visibility-is-scoped-own-clubs-commercial-summary-only)).
**Frontend work:** none yet — a minimal Club Settings "Platform Subscription" read-only summary card only (status, next due date, days remaining), sourced from the restricted view. The full Platform Owner Control Center UI is Phase 3c; the public-facing plan display is Phase 3d.
**Security work:** all platform billing tables verified inaccessible to any non-`platform_owner` role, including Club Owner, via direct query; `anon` role verified to have exactly `SELECT` on `public_plans` and `INSERT`-only on `contact_requests`, nothing else; every new RPC and `get_club_platform_access()`/`auth.club_write_allowed()` follow the [RLS_SECURITY.md](RLS_SECURITY.md) `SECURITY DEFINER` checklist.
**Tests:** effective status derivation correctness across all five states (`trial`/`active`/`grace_period`/`expired`/`cancelled`) purely from period dates + `now()`, no scheduled job; overlap prevention (two attempted concurrent/overlapping periods for one club — exactly one succeeds) and adjacent-renewal legality (`end_at` of period N = `start_at` of period N+1 succeeds); plan price edit does not retroactively change any existing period's snapshot; `auth.club_write_allowed()` per-category gating correct in all three access levels (`full`/`grace`/`blocked`) × three categories; `clubs.status = 'suspended'` forces `blocked` regardless of subscription standing; recording a payment restores `full` on next call with no stored-status update; Club Owner cannot access platform billing tables directly; unique partial index rejects a second non-cancelled trial for a club; `anon` SELECT on `public_plans` returns only published rows/safe columns, direct `anon` SELECT on `platform_plans` rejected, `anon` SELECT on `contact_requests` rejected.
**Exit gate:** a seeded test club's subscription can be created, renewed (producing a second period row linked via `previous_subscription_id`), left to lapse into `grace` then `blocked` (verified purely via date manipulation in tests, no time-travel mocking of a cron job since none exists), and restored via a recorded payment — with `clubs.status` never once changing during any of this. A seeded club can also be given a trial period and confirmed to go straight from `full` to `blocked` with no grace window. No non-Platform-Owner role can access platform billing tables directly. `anon` access is confirmed limited to exactly `public_plans` (read) and `contact_requests` (insert).

### Phase 3c — Platform Owner Control Center
**Goal:** Platform Owner has a real operational console for managing paying club customers, not a single flat screen (see [DECISIONS.md ADR-034](DECISIONS.md#adr-034--platform-owner-control-center-full-navigation-not-a-single-billing-screen)).
**Database work:** report RPCs/views backing each report below — no new tables, reads Phase 3b's schema.
**Frontend work:** `/platform` navigation wired to real data (shell exists from Phase 1). Per-club detail view `/platform/clubs/:clubId` (Overview, Current Subscription, Subscription History, Platform Payment History, Usage, Access Status, Audit) with an Actions panel: Activate, Start Trial, Renew, Change Plan, Extend Grace Period, Suspend Club, Reactivate Club, Cancel Subscription, Record Payment, Reverse Payment — each wired to its Phase 3b RPC. Platform Overview dashboard: total/active/trial/grace/expired/suspended club counts, subscriptions expiring soon, revenue collected today/month/year, renewals due, new clubs this month. `/platform/plans` (plan CRUD, publish/unpublish, reorder). `/platform/trials` (active trials, Trials Started/Active/Expired/Converted, conversion rate — see [DECISIONS.md ADR-044](DECISIONS.md#adr-044--platform-owner-reports-gain-trial-specific-metrics-public-leads-get-their-own-report)). `/platform/leads` (`contact_requests` inbox with status pipeline). Platform Reports: Subscription Report (club/plan/period/status/start/end/grace end/price/paid/outstanding), Revenue Report (by month/plan/club/payment method), Renewal Report (due in 7/15/30 days, grace period, expired, renewed), Growth Report (new/activated/renewed/expired/cancelled clubs), Usage Report (branches/fields/staff/customers/players/bookings/enrollments per club). In-app Alerts for subscriptions expiring soon, overdue renewals, and trials ending soon (rule-based, no external notification service — consistent with [PROJECT_BRIEF](../README.md) Section 59).
**Security work:** every screen and report verified Platform-Owner-only; every sensitive action (Suspend, Cancel, Reverse Payment, Extend Grace Period, Change Plan, Publish/Unpublish Plan) writes an `audit_logs` entry with actor/before/after/reason.
**Tests:** each report's output matches manually-verified totals against seeded multi-club test data (including at least one trial and one lead in the seed data); every Action button's RPC call is verified to require `platform_owner` and to write the correct audit entry; Club Owner attempting to reach any `/platform/*` route is redirected/rejected; Trials/Leads views correctly reflect seeded data.
**Exit gate:** Platform Owner can view the Overview dashboard with correct aggregate counts, drill into a specific club's full history, perform every listed Action successfully with a corresponding audit entry, manage plans (create/edit/publish/reorder) with edits never rewriting historical subscription snapshots, and view all five report types plus Trials and Leads against seeded data with figures that match manual verification.

### Phase 3d — Public Website + Signup + Onboarding + Trial
**Goal:** the end-to-end self-service conversion path works: anonymous visitor → operating club with an active trial. This is deliberately not deferred to project end — see the phase-ordering note at the top of this document.
**Database work:** `complete_new_club_onboarding()` — the single atomic RPC creating `clubs`/`branches`/`club_memberships`/trial `platform_subscriptions` together (see [ARCHITECTURE.md](ARCHITECTURE.md#signup--onboarding-strategy) for the full definition and [DECISIONS.md ADR-042](DECISIONS.md#adr-042--onboarding-finalization-is-one-atomic-rpc-client-never-sets-privileged-values)). Basic signup rate-limiting logic (DB-level, no external service — see [DECISIONS.md ADR-046](DECISIONS.md#adr-046--signup-rate-limiting-and-duplicate-club-flagging-are-lightweight-not-blocking)). Duplicate-club advisory flagging (see [DECISIONS.md ADR-045](DECISIONS.md#adr-045--duplicate-club-detection-flags-for-review-never-hard-blocks-signup)).
**Frontend work:** Public site pages within `PublicLayout` (built in Phase 1) — Home (Hero, Suitable For, Core Features, How It Works, Why Mala3by, Pricing preview reading `public_plans`, 7-Day Trial CTA, FAQ, Contact CTA), Pricing (`public_plans`-sourced cards, no hardcoded prices, no "Buy"/"Checkout" language), Contact (form → `contact_requests`), Terms, Privacy (static content acceptable for V1). `/login`, `/signup`, `/forgot-password`, `/reset-password` (Supabase Auth's built-in flows — no custom password-reset system). `/onboarding` 4-step wizard (Business Type → Basic Details → First Branch → Trial Activation confirmation) calling `complete_new_club_onboarding()`. Onboarding Success screen. Trial banner in `AppLayout` dashboard (days remaining, CTA to `/app/subscription`). First-Run Checklist (dismissible, not a wizard continuation — see [DECISIONS.md ADR-043](DECISIONS.md#adr-043--first-run-setup-is-a-checklist-not-a-multi-step-wizard)). `/app/subscription` screen (current plan, available plans, expiry, own payment history, "contact to activate" CTA — no self-service payment recording, see [DECISIONS.md ADR-035](DECISIONS.md#adr-035--club-owner-subscription-visibility-is-scoped-own-clubs-commercial-summary-only)). Route guards finalized: public routes need no auth, `/onboarding` needs auth + no existing membership, `/app/*` needs auth + membership + `full`/`grace` access, `/platform/*` needs `platform_owner`.
**Security work:** `complete_new_club_onboarding()` verified against the full [RLS_SECURITY.md](RLS_SECURITY.md) checklist — this RPC is the highest-risk one in the system since it's reachable with no prior membership to validate against; explicit tests that no client-supplied field can set `role_id`, `subscription_kind`, or trial duration.
**Tests:** see the full scenario in [USER_FLOWS.md](USER_FLOWS.md) Flow 8 and Flow 9; the [RLS_MATRIX.md](RLS_MATRIX.md) public-site verification checklist items (anon plan/lead access, onboarding RPC privilege boundaries, duplicate trial prevention, concurrent double-signup handling); Abuse Test Catalogue #1, #3, #12, #13 specifically (`club_id` spoofing, role spoofing, platform-owner-claim attempt, 365-day-trial-claim attempt).
**Functional Gate:** the full scenario from [USER_FLOWS.md](USER_FLOWS.md) Flow 8 passes end-to-end against a real (test) browser session — anonymous visitor sees current public plans, starts free trial, completes onboarding, club+branch+membership+trial created together, lands in `/app` with a correct trial banner, operates normally during trial. Flow 9 (expiry) passes via date manipulation in tests — new commitments blocked, existing data intact, Platform Owner sees it in `/platform/trials`, activating a paid plan restores access.
**Security Gate:** second user added to the same club does not create a second trial; `complete_new_club_onboarding()` passes the full [RLS_SECURITY.md](RLS_SECURITY.md) checklist — this RPC is the highest-risk one in the system since it's reachable with no prior membership to validate against; no client-supplied field can set `role_id`, `subscription_kind`, or trial duration under any payload manipulation (Abuse Test Catalogue #12, #13); an authenticated user with an existing club membership cannot call this RPC to create a second club.

### Phase 6 — Booking Engine (incl. Recurring Booking + Quick Field Block)
**Goal:** the core operational loop, concurrency-safe, including the two remaining booking-adjacent necessities per [DECISIONS.md ADR-047](DECISIONS.md#adr-047--recurring-booking-is-a-linking-table-over-real-individual-booking-rows-never-a-shortcut-around-conflict-checking)/[ADR-049](DECISIONS.md#adr-049--quick-field-block-requires-explicit-confirmation-when-existing-bookings-conflict).
**Database work:** `bookings` table (money columns `numeric(12,2)`) with generated `during` column + exclusion constraint blocking on `pending_payment`/`confirmed`/`checked_in` (see [DECISIONS.md ADR-021](DECISIONS.md#adr-021--exclusion-constraint-covers-pending_payment-confirmed-and-checked_in)); `create_booking` RPC covering validate→booking→invoice→optional payment→allocation in one transaction, with QR generation as a separate idempotent follow-up (`ensure_booking_qr`), never a hard dependency of the financial transaction. RPC additionally checks `auth.club_write_allowed(club_id, 'new_commitment')` (from Phase 3b) before creating a new booking. `booking_series` table + `create_recurring_booking` RPC (checks all requested occurrences against the exclusion constraint before confirming, creates N real `bookings` rows, never bypasses per-booking checks — see [USER_FLOWS.md](USER_FLOWS.md) Flow 1b). `field_blocks.type` finalized (`maintenance`/`weather`/`private_event`/`manual`/`holiday`) + `create_field_block` RPC (checks for conflicting existing bookings, never auto-cancels, surfaces conflicts for explicit decision).
**Frontend work:** day-view calendar grid (rows=slots, columns=fields), quick booking form (incl. Recurring toggle), booking detail/cancel, Quick Field Block action from the calendar.
**Security work:** RLS on `bookings`/`booking_series`/`field_blocks`; discount action gated by `booking.discount`/`booking.discount.apply`/`.override` permissions (see [SECURITY_ANTI_FRAUD.md](SECURITY_ANTI_FRAUD.md#discount-security)); `create_booking`/`create_recurring_booking`/`create_field_block` RPCs follow the [RLS_SECURITY.md](RLS_SECURITY.md) checklist; price is always server-recomputed at confirm, never trusted from the client (see [SECURITY_ANTI_FRAUD.md](SECURITY_ANTI_FRAUD.md#price-security)).
**Dependency:** Phase 3b (`auth.club_write_allowed`) must exist first.
**Tests:** concurrent booking attempt (two simultaneous inserts for the same slot — exactly one must succeed); exclusion constraint holds against direct RPC bypass attempts; boundary test confirming `10:00–11:00` and `11:00–12:00` do not overlap (and `10:30–11:30` does); recurring booking with a partial conflict correctly reports "N requested, M available" and never silently creates a partial series; field block creation over existing bookings correctly surfaces the conflict and never auto-cancels; client-submitted price manipulation attempt rejected (Abuse Test Catalogue #2).
**Functional Gate:** full reception booking flow works end-to-end including price calculation; a recurring booking series creates the correct number of linked bookings with conflicts explicitly surfaced; a field block correctly prevents new bookings and correctly surfaces existing conflicts instead of auto-cancelling.
**Security Gate:** double-booking is provably impossible under a concurrency test (Abuse Test Catalogue #5), not just "seems to work in manual testing"; recurring booking never bypasses the exclusion constraint for any individual occurrence; discount application respects the permission model, never a hardcoded UI limit.

### Phase 7 — Billing Core (incl. Outstanding Payments + CSV Export)
**Goal:** the financial ledger, plus the Outstanding Payments view and report export — both read-only additions over data this phase already owns, per [DECISIONS.md ADR-048](DECISIONS.md#adr-048--outstanding-payments-is-a-single-ledger-derived-view-not-a-new-stored-value).
**Database work:** `invoices` (numbering via `clubs.club_code`/`branches.branch_code`, never a hardcoded prefix), `invoice_items`, `payments` (**no `invoice_id` column** — see [DECISIONS.md ADR-011b](DECISIONS.md#adr-011b--paymentsinvoice_id-removed-payment_allocations-is-the-only-payment-invoice-relationship)), `payment_allocations` (the sole payment↔invoice link, with a trigger enforcing `SUM(amount) per payment_id ≤ payments.amount`), `refunds` (append-only, atomic RPC validating against refundable balance before insert — see [DECISIONS.md ADR-011c](DECISIONS.md#adr-011c--refund-model-refunds-table--reversing-allocation-atomic-rpc)), `invoice_number_sequences` + numbering RPC + RLS, `outstanding_invoices` view. All money columns `numeric(12,2)`. Payment/refund RPCs check `auth.club_write_allowed(club_id, 'settle_existing')` — this is the category deliberately still **allowed** when a club's derived platform-subscription access is `grace` (see [DECISIONS.md ADR-033](DECISIONS.md#adr-033--platform-access-is-full--grace--blocked-derived-by-one-centralized-db-function)), distinct from `platform_payments` in Phase 3b, which is the club paying *Mala3by*, not its own customers. **Issued invoice lock enforced**: no free-form update path once `invoices.status = 'issued'` (see [SECURITY_ANTI_FRAUD.md](SECURITY_ANTI_FRAUD.md#issued-invoice-lock)) — correction is void + reissue only.
**Frontend work:** invoice view, payment collection form, refund flow, A4 + 80mm print CSS, `/app/outstanding` screen (filters: All/Due Today/Overdue/Academy/Bookings), CSV export on this and other applicable reports (client-side generation, no library — see [ARCHITECTURE.md](ARCHITECTURE.md#reporting-strategy)).
**Tests:** invoice numbering under concurrent calls (parallel connections, no duplicate/gap issues); allocation-sum check trigger; refund flow leaves the ledger consistent and cannot exceed refundable balance even under concurrent refund attempts on the same payment (Abuse Test Catalogue #6); attempt to edit an issued invoice's items/total/customer directly is rejected (Abuse Test Catalogue #9); attempt to hard-delete a payment is rejected (Abuse Test Catalogue #10); `outstanding_invoices` figures match manual ledger calculation on seeded data; CSV export respects the same club/branch/permission/filter scoping as the on-screen view — a URL/parameter manipulation attempt to export another club's data is rejected identically to viewing it.
**Functional Gate:** booking produces a correctly numbered invoice; partial payment + refund both reflected correctly in the derived outstanding balance (computed from `payment_allocations`, not any stored `amount_paid` column); both print layouts render correctly on paper or accurate print-preview; `/app/outstanding` shows correct figures with working filters; CSV export downloads a correctly-scoped file.
**Security Gate:** no hard delete possible on `invoices`/`payments`/`payment_allocations`/`refunds`; issued invoices cannot be silently edited; refund cannot exceed refundable balance even under concurrency; export cannot leak cross-club data via any client-side manipulation.

### Phase 8 — QR + Scanner + Check-in
**Goal:** secure check-in with a clear separation between validation and mutation.
**Database work:** `qr_credentials` (`type`: `booking` | `player_membership` only; `single_use` varies by type) + `qr_scan_events` (every scan logged, regardless of outcome) + RLS. Two RPCs for booking check-in: a read-only validate/lookup, and a separate atomic confirm-check-in that consumes the credential and transitions `bookings.status → checked_in` together (see [DECISIONS.md ADR-011e](DECISIONS.md#adr-011e--qr-scan-validates-explicit-staff-confirmation-performs-the-check-in-mutation)). Player QR validation never mutates the credential.
**Frontend work:** `/scan` PWA page with camera access, QR generation on booking confirm, validate-then-confirm check-in UI (two explicit steps, not one), check-in result screen (four unambiguous outcomes: VALID / ALREADY USED / EXPIRED / INVALID, plus WRONG CLUB).
**Security work:** token hashing verified end-to-end (raw token never persisted); offline fail-closed + manual override path with audit logging; scan/confirm RPCs follow [RLS_SECURITY.md](RLS_SECURITY.md).
**Tests:** replay test (second confirm attempt on a consumed token fails cleanly, Abuse Test Catalogue #7); expiry test; wrong-club token test; player QR scanned twice in a row both succeed (reusable, not consumed) with two `qr_scan_events` rows; a scan alone (no confirm) never changes `bookings.status`.
**Functional Gate:** booking → QR → scan (validate) → confirm → check-in works on a real phone camera; every scan attempt — successful or not — appears in `qr_scan_events`.
**Security Gate:** replay of the confirm step is blocked and clearly reported with original timestamp/staff (Abuse Test Catalogue #7); token hashing verified end-to-end (raw token never persisted or logged); no bare booking/player ID ever appears in QR content.

### Phase 11 — Enrollment + Subscriptions + Installments
**Goal:** academy revenue lifecycle.
**Database work:** `enrollments` with concurrency-safe capacity check RPC (`SELECT ... FOR UPDATE` on `groups`, re-validated inside the same transaction as the insert), `subscriptions` (`enrollment_id` unique — one subscription per enrollment, a deliberate rule, see [DECISIONS.md ADR-013b](DECISIONS.md#adr-013b--one-subscription--one-enrollment-in-v1-is-a-deliberate-rule)), `subscription_freezes` + effective-expiry derivation RPC (freeze extends expiry per [DECISIONS.md ADR-008](DECISIONS.md#adr-008--subscription-freeze-extends-expiry-by-default) — `subscriptions.end_date` is never overwritten in place, only the derived `effective_end_date` reflects freeze extensions). Activation RPC branches on `clubs.subscription_activation_policy` (`manual` | `first_payment` [default] | `full_payment` — see [DECISIONS.md ADR-013](DECISIONS.md#adr-013--subscription-activation-policy-is-a-club-setting-not-a-hardcoded-rule)). Enrollment/subscription creation RPCs check `auth.club_write_allowed(club_id, 'new_commitment')`; installment payments against an existing subscription use `'settle_existing'`, same as Phase 7.
**Frontend work:** enrollment wizard (guardian→player→program→group→subscription→invoice→payment), freeze UI, installment schedule view, a simple activation-policy dropdown in club settings.
**Tests:** installment/outstanding-balance correctness against the ledger (via `payment_allocations`); freeze correctly derives `effective_end_date` without mutating `end_date`; expiry transition test; concurrent enrollment race test (two receptionists enrolling into the last group spot — exactly one succeeds, Abuse Test Catalogue #8); each of the three activation policy values produces correct activation behavior.
**Functional Gate:** full enrollment flow works end-to-end and activates per the club's configured policy; freeze correctly pauses and the derived effective expiry extends.
**Security Gate:** a full concurrency test proves group capacity cannot be oversold under any timing (Abuse Test Catalogue #8); subscription creation without required payment/permission per the club's activation policy is rejected, never silently allowed.

### Phase 12 — Sessions + Attendance

## Build Order Rationale (summary)

1. **RLS before any domain data** — the tenant boundary is the one thing every later phase must inherit for free; retrofitting it onto live data is the most expensive possible rebuild.
2. **Platform Billing data model (3b) immediately after Staff/Permissions, before any customer-facing domain** — every subsequent write-heavy RPC (booking, payment, enrollment) calls `auth.club_write_allowed()`, so `get_club_platform_access()` and the tables behind it must exist first, not be retrofitted into already-built RPCs later. The full Control Center UI (3c) can follow later without blocking anything else, since nothing downstream depends on the *UI* existing — only the *function*.
3. **Public site + signup + trial (3d) immediately after the Control Center (3c), not deferred to project end** — explicit instruction: the self-service trial is the primary conversion path and has no reason to wait. It only depends on Auth (2), the trial/subscription machinery (3b), a place to land new users (1's `AppLayout`), and Platform Owner visibility into trials (3c) — all of which are already in place by this point. Landing it here also means every subsequent phase's manual QA can exercise the real signup→trial→operate path instead of only ever testing against hand-seeded database rows.
4. **Booking before Academy** — proves the exclusion-constraint/RPC/QR/invoice pattern once; Academy then reuses the same billing/QR infrastructure instead of a parallel implementation.
5. **Dashboards/reports placed right after the data that feeds them exists**, not deferred to one late mega-phase — avoids a late integration phase that's really just "go query things built weeks ago."
6. **Audit + hardening as its own late phase**, added to tables that are already stable — cheaper and less error-prone than building audit alongside a still-changing schema.
