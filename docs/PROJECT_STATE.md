### Phase 6 hardening — booking_series_id trust boundary: COMPLETE
- **Issue (user-flagged, post-commit review):** `create_booking`'s `p_booking_series_id` parameter, even with a same-club existence check, let any caller holding `booking.create` in a club attach a standalone booking to *any* other series in that club — a different customer's series, a different field's series, someone else's series entirely. Bookkeeping corruption, not a privilege escalation in the strict RLS sense, but an unvalidated trust boundary that shouldn't have existed.
- **Fix (Option A — the stronger of the two offered):** split into a private `_create_booking_internal` (accepts `p_booking_series_id`, zero EXECUTE grants to any client role — `anon`/`authenticated`/`public` all revoked, confirmed unreachable via a direct call returning `permission denied` even from an authorized club member) and a public `create_booking` with **no series parameter at all** — a standalone booking created through the public path cannot be attached to a series by construction, not merely by validation. `create_recurring_booking` calls the internal function directly with its own freshly-created series id. Kept a defense-in-depth same-club+same-field+same-customer check inside the internal function too, in case its access is ever accidentally widened later.
- Migration `20260815240000_phase6_harden_booking_series_id.sql`. Old 10-arg `create_booking` signature explicitly dropped so it can't remain callable alongside the new 9-arg one.
- **All 4 requested abuse tests proven directly against live data:** (1) nonexistent/random series id and (3) unauthorized series — both structurally impossible now, proven by calling `_create_booking_internal` directly as an authorized club member and getting `permission denied for function _create_booking_internal` (not a logic rejection — the function is genuinely unreachable); (2) series from another club — same structural proof, no path exists to attempt it; (4) valid series through the legitimate `create_recurring_booking` flow — 3 occurrences requested, 3 created, each with its own distinct `invoice_id`, all correctly linked to the same `booking_series_id`. Also directly confirmed a booking made through the public `create_booking` always has `booking_series_id = null`.

- **Real defect found and fixed via live browser smoke testing** (not caught by `get_advisors` or SQL-level RLS testing): `anon` requests to `public_plans` failed with `401 permission denied for function is_platform_owner`. ## Final Two Decisions Closure Log (2026-08-15, final two decisions)

Full detail in [DECISIONS.md](DECISIONS.md) ADR-051, ADR-052.

1. **Automatic Trial Entitlement** (ADR-051) — one automatic trial per user account via new `automatic_trial_entitlements` table (unique `user_id`), independent of and additional to the existing one-trial-per-club rule; concurrency-safe via the unique-constraint-as-guard pattern, no `SELECT`-then-`INSERT` race
