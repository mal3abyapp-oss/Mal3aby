# Mal3aby — Production Database Backup Runbook

Written 2026-08-31 as part of the Controlled Commercial Launch Gate.
Zero new paid service. No Supabase plan upgrade (standing, explicit,
already-decided user decision — accepted risk, not re-litigated here).

## Why this exists

Supabase's Free plan has **zero automated backups and no PITR**
(confirmed live, re-confirmed every phase this engagement —
`BACKUP_RECOVERY_PLAN.md`). This runbook is the independent,
no-new-paid-service mitigation: a manual, operator-run logical backup
procedure using tools already available.

## Why this is NOT a plain `pg_dump`

`supabase db dump` (the CLI's own wrapper) requires a working Docker
daemon to run `pg_dump` inside a container. **In this environment,
Docker Desktop's Windows service is confirmed `Stopped`
(`Get-Service com.docker.service`), and no standalone `pg_dump` binary
exists anywhere on this machine** (checked: no system PATH entry, the
local `C:\Program Files\PostgreSQL\17` install has an empty `bin\`
directory — a stub install with no client tools). `supabase db dump`
was attempted and hangs indefinitely under these conditions (confirmed:
the process stays alive with near-zero CPU, blocked waiting on the
unreachable Docker daemon, not failing fast).

**The functional equivalent used instead**: SQL introspection via
`pg_catalog`/`information_schema`, executed directly against production
through the Supabase MCP's `execute_sql` tool (the same tool used for
every read-only inspection throughout this entire engagement). This
produces the same categories of output a real `pg_dump --schema-only`
+ a data-only dump would (table DDL, function DDL, constraints,
indexes, RLS policies, grants, and full row data as INSERT
statements) — just generated by directly querying Postgres's own
system catalogs instead of shelling out to the `pg_dump` binary.

**If Docker becomes available in a future environment**, prefer the
real `supabase db dump --linked` command instead — it is more complete
and battle-tested. This runbook's SQL-introspection method remains a
valid fallback whenever Docker/pg_dump genuinely isn't available.

## What one backup captures

A backup is a timestamped directory under `backups/<UTC-timestamp>/`
containing:

| File | Contents |
|---|---|
| `01_tables.sql` | Every `public` schema table's column definitions (`CREATE TABLE IF NOT EXISTS`) |
| `02_functions.sql` | Every function's full definition (`pg_get_functiondef`) |
| `03_constraints.sql` | Every constraint (PK/FK/unique/check/exclusion) via `pg_get_constraintdef` |
| `04_indexes.sql` | Every index definition |
| `05_rls_enable.sql` | `ENABLE`/`FORCE ROW LEVEL SECURITY` for every RLS-protected table |
| `06_rls_policies.sql` | Every RLS policy, reconstructed as `CREATE POLICY` |
| `07_grants.sql` | Every real (anon/authenticated/service_role/postgres) EXECUTE and table grant |
| `08_data.sql` | Every real row in every `public` schema table, as `INSERT` statements |
| `09_manifest.json` | SHA-256 checksum + size for every file above, plus explicit exclusions and a security review note |

**Explicitly NOT captured** (see `09_manifest.json`'s `not_captured`
block for the full, current-as-of-backup-time list):
`auth.users`/`auth.*` (real user credentials — restoring this backup
does NOT restore anyone's ability to log in with their existing
password), Supabase Storage file *contents* (only counted, not
exported), Edge Function source (already in git), Cloudflare Worker
secrets (never exportable this way — see `INCIDENT_RUNBOOKS.md`'s
Secret Leak runbook), Supabase project dashboard-level configuration.

## How do I create a backup?

1. Confirm the working directory is the repo root (`D:\Ai Projects\Mal3aby`).
2. Create a fresh timestamp directory:
   ```bash
   TS=$(date -u +%Y%m%dT%H%M%SZ)
   mkdir -p "backups/$TS"
   echo "$TS" > backups/.last_ts
   ```
3. Run each numbered extraction query below via the Supabase MCP
   `execute_sql` tool against `project_id=gxkrtlvpjwxhcqdisyob`. Each
   query is self-contained and aggregates its entire result server-side
   into one string, so it comes back as either (a) inline text you
   write directly to the target file, or (b) — if it exceeds the tool's
   inline token limit — automatically saved to a local tool-result
   file, which you then extract with:
   ```bash
   python3 backups/extract_result.py "<saved-tool-result-path>" "backups/$TS/<NN_name>.sql" "<column_alias>"
   ```
4. **01_tables.sql**:
   ```sql
   with cols as (
     select c.oid as table_oid, n.nspname as schema_name, c.relname as table_name,
       string_agg(format('  %I %s%s%s', a.attname, pg_catalog.format_type(a.atttypid, a.atttypmod),
         case when a.attnotnull then ' NOT NULL' else '' end,
         case when ad.adbin is not null then ' DEFAULT ' || pg_get_expr(ad.adbin, ad.adrelid) else '' end
       ), E',\n' order by a.attnum) as columns_ddl
     from pg_class c
     join pg_namespace n on n.oid = c.relnamespace
     join pg_attribute a on a.attrelid = c.oid and a.attnum > 0 and not a.attisdropped
     left join pg_attrdef ad on ad.adrelid = c.oid and ad.adnum = a.attnum
     where n.nspname = 'public' and c.relkind = 'r'
     group by c.oid, n.nspname, c.relname
   )
   select string_agg(format('CREATE TABLE IF NOT EXISTS %I.%I (%s%s%s\n);', schema_name, table_name, E'\n', columns_ddl, E'\n'), E'\n\n' order by table_name) as tables_ddl
   from cols;
   ```
5. **02_functions.sql**:
   ```sql
   select string_agg('CREATE OR REPLACE FUNCTION ' || pg_get_functiondef(p.oid) || E';\n', E'\n') as functions_ddl
   from pg_proc p join pg_namespace n on n.oid = p.pronamespace
   where n.nspname = 'public';
   ```
6. **03_constraints.sql**:
   ```sql
   select string_agg(format('ALTER TABLE %I.%I ADD CONSTRAINT %I %s;', n.nspname, c.relname, con.conname, pg_get_constraintdef(con.oid)), E'\n' order by c.relname, con.conname) as constraints_ddl
   from pg_constraint con
   join pg_class c on c.oid = con.conrelid
   join pg_namespace n on n.oid = c.relnamespace
   where n.nspname = 'public';
   ```
7. **04_indexes.sql**:
   ```sql
   select string_agg(indexdef || ';', E'\n' order by indexname) as indexes_ddl
   from pg_indexes
   where schemaname = 'public'
     and indexname not in (select conname from pg_constraint where contype in ('p','u'));
   ```
8. **05_rls_enable.sql**:
   ```sql
   select string_agg(format('ALTER TABLE %I.%I ENABLE ROW LEVEL SECURITY; ALTER TABLE %I.%I FORCE ROW LEVEL SECURITY;', schemaname, tablename, schemaname, tablename), E'\n' order by tablename) as rls_enable_ddl
   from pg_tables t
   where schemaname = 'public'
     and exists (select 1 from pg_class c join pg_namespace n on n.oid=c.relnamespace where n.nspname=t.schemaname and c.relname=t.tablename and c.relrowsecurity);
   ```
9. **06_rls_policies.sql**:
   ```sql
   select string_agg(format('CREATE POLICY %I ON %I.%I FOR %s TO %s%s%s;', policyname, schemaname, tablename, cmd, array_to_string(roles, ', '),
     case when qual is not null then ' USING (' || qual || ')' else '' end,
     case when with_check is not null then ' WITH CHECK (' || with_check || ')' else '' end
   ), E'\n' order by tablename, policyname) as policies_ddl
   from pg_policies where schemaname = 'public';
   ```
10. **07_grants.sql** — run BOTH of these and append the second to the same file (`echo "" >> backups/$TS/07_grants.sql` between them):
    ```sql
    select string_agg(format('GRANT EXECUTE ON FUNCTION %I.%I(%s) TO %I;', n.nspname, p.proname, pg_get_function_identity_arguments(p.oid), g.grantee), E'\n' order by p.proname, g.grantee) as function_grants_ddl
    from information_schema.role_routine_grants g
    join pg_proc p on p.proname = g.routine_name
    join pg_namespace n on n.oid = p.pronamespace and n.nspname = g.routine_schema
    where g.routine_schema = 'public' and g.grantee in ('anon','authenticated','service_role','postgres');
    ```
    ```sql
    select string_agg(format('GRANT %s ON TABLE %I.%I TO %I;', privilege_type, table_schema, table_name, grantee), E'\n' order by table_name, grantee, privilege_type) as table_grants_ddl
    from information_schema.role_table_grants
    where table_schema = 'public' and grantee in ('anon','authenticated','service_role','postgres');
    ```

    which is what caused the now-resolved restore-ordering bug).

    server-side, no per-table round trips needed), iterating an explicit

## Where is it stored?

Locally, under `backups/<timestamp>/` in this repository — **gitignored**
(`.gitignore`'s `/backups/` rule, added specifically for this purpose;
verified via `git check-ignore -v`). This directory is NEVER committed.

**This is a single point of failure by itself** (one machine, one
disk). The directive's own guidance ("prefer resources already
available... if fully automated off-site storage cannot be safely
configured using existing resources/credentials, create the safest
executable local/operator workflow instead of inventing credentials")
is honestly reflected here: **no automated off-site copy exists yet**.
The operator should manually copy the timestamped backup directory to
at least one independent location (a personal cloud drive, an external
drive, etc.) after each backup run — this is a deliberate, disclosed
gap, not a hidden one. See "Retention" below.

## How do I verify checksum?

```bash
python3 backups/verify_manifest.py "backups/<timestamp>"
```
Re-computes SHA-256 for every file listed in that backup's
`09_manifest.json` and reports PASS/FAIL per file. A FAIL means the
file was modified or corrupted after the backup was created — treat
that backup as untrustworthy and re-run a fresh one.

## How do I know a backup failed?

- Any of steps 4-11 above returning an error instead of the expected
  aggregated result.
- `08_data.sql`'s row count sanity check: `grep -c "no rows" backups/<ts>/08_data.sql`
  plus `grep -c "^INSERT INTO" backups/<ts>/08_data.sql` should together
  account for every table — cross-check against
  `select count(*) from pg_tables where schemaname='public';` at backup
  time.
- `verify_manifest.py` reporting any checksum FAIL.
- A `09_manifest.json` that's missing or has fewer than 8 entries in
  `files[]`.

## How long do I retain it?

Recommended target (storage permitting): **7 daily + 4 weekly**. Not
automated in this pass (would require a scheduler running independently
of this session, which Section 49/Foreground-Only explicitly
prohibits creating). Manual retention procedure:

```bash
# List backups older than 7 days that are NOT the first backup of their week
# (a simple, safe, human-reviewable retention pass -- run manually, review
# before deleting, never delete the most recent backup regardless of age)
ls -1 backups/ | grep -E '^[0-9]{8}T[0-9]{6}Z$' | sort
```
Delete old backup directories manually after confirming a newer one
exists and passes `verify_manifest.py`. Never delete the only existing
backup.

## How do I restore it?

**Never restore over production.** Restore into an isolated target only.

1. Provision a target Postgres 17 database (a fresh Supabase project,
   or a local Postgres instance if one becomes available).
2. Apply in this exact order (foreign keys and functions have real
   dependencies):
   ```
   01_tables.sql        -- tables first, no data yet
   03_constraints.sql   -- PK/FK/unique/check (needs tables to exist)
   04_indexes.sql
   02_functions.sql     -- functions may reference tables (SECURITY DEFINER bodies), safe once tables exist
   05_rls_enable.sql
   06_rls_policies.sql  -- policies reference functions like has_permission() -- must come after 02
   07_grants.sql
   08_data.sql           -- data last, once every constraint/policy exists
   ```
3. **FK ordering (fixed 2026-09-03, corrected same day per independent
   P2 verification)**: `08_data.sql`'s `INSERT`
   statements are generated in an explicit, verified topological order
   (`backups/topo_sort_tables.py`'s `restore_order`, computed from every
   NOT NULL foreign key in the live schema — 160 hard edges across the
   114 tables, confirmed a valid DAG with zero cycles both by Kahn's
   algorithm and an independent DFS cross-check). Nullable and
   self-referencing FK columns whose real value could still point
   forward to a not-yet-loaded table are inserted as `NULL` and
   restored by a second block of deferred `UPDATE` statements appended
   to the end of `08_data.sql`, run only after every table's `INSERT`
   block above it has completed. Applying `08_data.sql` top-to-bottom
   in one pass, in file order, should no longer hit an FK violation
   from insert ordering. **This has been dry-run verified against the
   live schema** (topological order computed and cross-checked, zero
   FK-hard-edge violations in the resulting order) but **has not yet
   been executed against a real restore target** — see "What has and
   hasn't been rehearsed" below for the precise, current boundary. If a
   future schema change reintroduces an FK cycle among NOT NULL
   columns, `topo_sort_tables.py --verify` will fail loudly (exit 1)
   rather than silently producing a broken order — treat that as a
   schema-design problem to fix (e.g. make the new FK nullable or
   deferrable), not something to route around in the backup script.
4. Run the Post-Restore Verification checks in `INCIDENT_RUNBOOKS.md`.

## What has and hasn't been rehearsed

- **Verified (dry-run, against the live production schema, read-only,
  2026-09-03, re-confirmed same day after correcting a stale 2-table
  snapshot found by independent verification)**: the corrected
  FK-dependency restore order is a valid
  topological sort of all 114 tables' 160 NOT NULL foreign keys —
  computed via Kahn's algorithm, independently cross-checked via DFS
  cycle detection (different algorithm, same result: 0 cycles), and
  confirmed to produce zero ordering violations against every hard
  edge. The nullable/self-referencing nulled-then-deferred-UPDATE
  design was checked against real row counts in production (142
  `bookings.invoice_id`, 34 `subscriptions.invoice_id`, 12 each for
  `club_membership_subscriptions.invoice_id` and `shop_sales.invoice_id`,
  and smaller counts elsewhere — all genuinely non-NULL forward
  references that would have broken a naive single-pass restore even
  with the table order fixed, which is why the defer mechanism exists
  and is not optional).
- **NOT executed**: no actual `CREATE TABLE`/`INSERT`/`UPDATE` from any
  backup has been run against any real Postgres target, in this repo's
  history to date. The reason is a genuine environment constraint, not
  a choice: this project's Supabase organization is confirmed on the
  **`free`** plan (`get_organization`, re-confirmed live 2026-09-03),
  and creating a disposable Supabase branch (the safe, standard way to
  rehearse a restore without touching production or another real
  project) requires the `create_branch` MCP tool's `confirm_cost_id` —
  i.e. branching is a billable operation not available on the free
  tier without a plan/cost decision. That decision belongs to the user
  (see `BACKUP_RECOVERY_PLAN.md`'s standing, already-accepted Stop
  Condition), not to an autonomous session. The only other Supabase
  project reachable from this environment (`mat3amos-dev`) is a real,
  separate, unrelated live application — restoring into it would
  contaminate someone else's real project, not provide a disposable
  target. A local Postgres instance was also unavailable (Docker
  Desktop's Windows service confirmed `Stopped`, no standalone
  `pg_dump`/`psql`/`postgres` binaries found on this machine — see
  "Why this is NOT a plain `pg_dump`" above). **A true end-to-end
  restore rehearsal (fresh target → apply all 9 files in order →
  post-restore verification queries pass) remains genuinely
  unperformed.** This is the one part of this finding that stays open;
  it requires either a paid Supabase branch/project (user decision) or
  a working local Postgres install becoming available in a future
  session.

## What is NOT included? (repeated for visibility)

`auth.users`/`auth.identities` (Supabase Auth identities), Storage file
contents, Cloudflare Worker secrets, Supabase project dashboard
configuration. See `09_manifest.json`'s `not_captured` block for the
authoritative, backup-specific list.

## What must be restored separately? (precise operational boundary,
re-verified 2026-09-03 against Supabase's own current documentation and
this project's live database — not left vague)

- **Auth users** (`auth.users`, 40 real users confirmed live in this
  project): the SQL-introspection method this backup already uses
  *could* technically read `auth.users` too — **corrected**: it is a
  plain Postgres table like any other and IS reachable via the same
  `execute_sql` tool this whole procedure runs on (`select * from
  auth.users` succeeds; confirmed live, `40` rows). A prior version of
  this document wrongly stated this needs `service_role`/dashboard
  access unavailable to this session — that was inaccurate and has
  been corrected here. **The real, still-unresolved boundary is
  restore, not export**: Supabase's own documentation (Guides →
  Self-Hosting → "Restore a Platform Project to Self-Hosted") confirms
  `auth.users` restore is only supported via `supabase db dump`
  (Docker-dependent — unavailable in this environment, see "Why this
  is NOT a plain `pg_dump`" above) followed by a raw `psql` restore
  with `session_replication_role = replica` to bypass triggers, run as
  ONE step alongside `auth.identities`, `auth.sessions`, and every
  other `auth.*` table together — GoTrue enforces invariants across
  those tables (linked `identities` rows, specific `encrypted_password`
  hash formats [bcrypt/Argon2 only], `instance_id`, MFA factor
  consistency) that a partial, hand-assembled `INSERT` into `auth.users`
  alone would not satisfy correctly. The supported *programmatic*
  alternative for creating/restoring individual users outside a full
  `pg_dump`/`psql` cycle is the Auth Admin API
  (`supabase.auth.admin.createUser()`, accepting either a
  `password_hash` or plaintext `password`) — but that requires the
  `service_role` key (available to the connector/backend, not to this
  MCP session) and would need to be run as 40 individual API calls,
  not a SQL batch. **Conclusion**: `auth.users` CAN be exported today
  (trivial to add to a future backup pass — was simply never added, not
  blocked); it CANNOT be correctly restored by this repo's SQL-level
  backup/restore tooling alone, by Supabase's own design, regardless of
  Docker availability — a real database restore of business data would
  leave every existing user needing to reset their password via normal
  Supabase Auth password-reset flow (its own working, unaffected
  mechanism) rather than losing access to the platform entirely.
- **Storage files**: would need a separate bucket-level copy (Supabase
  Storage API, `service_role`-authenticated) — not performed this pass;
  confirmed via Supabase's own self-hosted restore guide this is
  never included in a database-level dump/restore, on any plan, by
  design ("Transferring storage objects... is not covered").
- **Secrets**: re-provisioned per `INCIDENT_RUNBOOKS.md`'s Secret Leak /
  Secret Rotation runbook — never stored in any backup file.

## Reusable scripts

- `backups/extract_result.py` — pulls a large query result out of a
  saved MCP tool-result file into the target backup file.
- `backups/make_manifest.py` — generates `09_manifest.json` with real
  SHA-256 checksums for a given backup directory.
- `backups/verify_manifest.py` — re-checks those checksums against the
  files currently on disk.
- `backups/topo_sort_tables.py` — computes the FK-dependency-safe table
  restore order (`--json` for `restore_order`, `--defer-cols` for
  `defer_cols`, `--verify` for a fast pass/fail DAG check) used to
  generate `08_data.sql`'s table iteration order and deferred-update
  column list (see step 11 above). Regenerate both blocks from this
  script — never hand-edit them — whenever the schema's tables or
  foreign keys change.

No secrets are embedded in any of these scripts — they operate purely
on already-extracted local files (or, for `topo_sort_tables.py`, a
static edge list refreshed from a read-only schema query) and take no
credentials as arguments.
