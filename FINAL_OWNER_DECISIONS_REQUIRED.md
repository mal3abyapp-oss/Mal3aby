# Platform Owner Control Plane V1 — Phases 4+5 (Tenant 360 + Last Activity)

Added 2026-09-08, branch `feature/platform-owner-control-plane-v1`, scoped strictly to Tenant 360 (`PlatformClubDetailPage.tsx`) and Last Activity per the mission brief. Product-judgment decisions this mission made on its own, with the reasoning, so they can be revisited if the owner disagrees:

## 6. "Last activity" definition — chosen: MAX(booking placed, payment received, academy attendance marked), any status

The RPC (`get_platform_club_last_activity`, in `supabase/migrations/20260908160000_platform_club_360_academy_count_and_last_activity.sql`) defines "last meaningfully active" as the most recent of `bookings.created_at`, `payments.received_at`, or `attendance.marked_at` — **deliberately including cancelled bookings and voided payments**, unlike `count_active_customers_and_players()`'s active-player definition (which excludes both, since that RPC counts current commercial usage, not historical activity). The judgment call: a cancelled booking or a later-reversed payment still reflects a real person at the club taking a real action at that moment — excluding it would make a club that had recent-but-cancelled activity look more dormant than it actually was. If the owner would rather this signal match the stricter "qualifying activity" definition exactly (excluding cancelled/void), that's a one-line change to both this RPC and its `search_platform_clubs()` inline copy.

**Not included**: staff login/last-seen (no such column exists anywhere in the schema — would require new infrastructure, explicitly out of scope for V1), WhatsApp message activity (already shown separately as its own "WhatsApp health" card — folding it into "last activity" would blur two distinct signals the console currently keeps separate).

## 7. `get_platform_club_360()` extended in place rather than a new RPC

The mission allowed either approach. Chose to extend `get_platform_club_360()` with two new trailing columns (`academy_count`, plus `last_activity_at`/`last_activity_type` delegating to the new standalone `get_platform_club_last_activity()` RPC) rather than have Tenant 360 fire a second round trip, since: (a) only one frontend call site exists for `get_platform_club_360()` (confirmed by grep), so extending it is safe and byte-preserves every existing column; (b) the page's own prior history (its "Phase C" comment) already established the principle of one batched RPC over per-section queries for this exact page. The standalone `get_platform_club_last_activity()` RPC still exists independently (not just inlined) so the Tenant 360 page can show its own isLoading/isError state for last-activity specifically, decoupled from the larger club-360 read.

## 8. Last Activity added to the Clubs list (`PlatformClubsPage.tsx`), not skipped

The mission flagged the N+1 risk explicitly. Judged safe to add: `search_platform_clubs()` already computes exactly one row per club inside a single server-side query plan (real `LIMIT`/`OFFSET` pagination, not a client-side loop) — adding two more correlated-subquery columns to its existing `computed` CTE is the same cost shape as every other column already there (branch_count-style pattern used elsewhere in this codebase), not a new per-row RPC call. This is architecturally distinct from the N+1 anti-pattern the deep dive flagged on `PlatformOwnersPage`/`PlatformAuditPage` (client-side unbounded accumulation), which this change does not touch.

## 9. Hard-limit card status vocabulary: NORMAL/NEAR LIMIT/OVER LIMIT only, no GRACE

Added NORMAL/APPROACHING_LIMIT(80%)/OVER_LIMIT differentiation to the branch/field/academy hard-limit card, matching the 80% threshold `get_commercial_usage()` already uses for its own hard-limit branch. Deliberately did **not** add a GRACE state to this card — grace periods only apply to the two *controlled* resources (staff/active-player), which already have their own full status card (`CommercialUsageAndFoundingOfferCard`) with unlimited/normal/approaching_limit/grace/over_limit. Branch/field/academy limits are hard-enforced at the database trigger level (blocks new inserts outright) with no grace mechanism in the schema — inventing a GRACE label for them would misrepresent how they actually behave.

## 10. Government Compliance card: kept the "un-affiliated club renders nothing" default

Fixed the loading/error branches (previously silent either way) but kept the existing behavior that a genuinely un-affiliated club (the common case — most clubs have no government/ministry collection relationship) shows no card at all, rather than an explicit "Not affiliated" card every time. Judgment: a permanent visible card for the ~all-clubs-unaffiliated common case would be noise; the fix that matters is making "failed to load" and "loading" visually distinct from that silent default, which is now done. If the owner would prefer an explicit always-visible "Not affiliated" state instead of silence, that's a small follow-up change.

**Files touched this mission**: `supabase/migrations/20260908160000_platform_club_360_academy_count_and_last_activity.sql` (new RPC + 2 extended RPCs + 2 new indexes), `src/features/platform/PlatformClubDetailPage.tsx`, `src/features/platform/PlatformClubsPage.tsx`, `src/lib/supabase/types.ts` (manually patched to match the migration — Supabase MCP was blocked this session, so `generate_typescript_types` could not be run; regenerate for real once the migration is applied), `src/lib/i18n/resources/{en,ar}/common.json`. `npx tsc -b --force` and `npx eslint` both clean on all touched files. Migration was written but **not applied** to any database, per this mission's explicit instruction.

# Platform Owner Control Plane V1 — Phases 7+8 (Attention Center + WhatsApp Platform Visibility)

Generated 2026-09-08, branch `feature/platform-owner-control-plane-v1`. Genuinely ambiguous product-judgment calls made while implementing Phase 7 (Attention Center) and Phase 8 (WhatsApp Platform Visibility), per the mission directive's own instruction to document rather than silently pick a side. Nothing below blocked shipping — each decision was made with the most defensible, most conservative reading of the mission brief, and is reversible.

## 6. Phase 8: WhatsApp usage screen placement — chose Reports tab (b) over Overview card (a)

The mission offered two options. Chose **a new "WhatsApp" tab on `PlatformReportsPage.tsx`**, not a summary card on Overview, because:
- `get_whatsapp_usage_platform_wide()` returns one row per club with 6 columns (30d/7d message counts, delivered, failed, last-message timestamp) — this is genuinely tabular, per-tenant, drill-down data, not a single platform-wide summary number a card format could honestly represent without losing the per-club detail the mission explicitly asked to preserve ("which tenants are affected").
- It matches this page's existing, already-established 5-tab pattern (Subscription/Revenue/Renewal/Growth/Usage) exactly — same `DataTable` + club-link-to-Tenant-360 convention every other tab already uses, so no new UI pattern was introduced.
- A card would have forced either an oversimplified aggregate (losing per-club visibility) or an awkward mini-table crammed into a card, neither of which fits this console's established design language as well as a sixth tab does.

If you'd prefer a small "WhatsApp volume" summary card on Overview *in addition to* the Reports tab (e.g., total messages/failures this month, linking through to the new tab), that's a straightforward follow-up — not built here to avoid presenting the same data twice without being asked.

## 7. Phase 8: fixed a fixture-filtering gap in `get_whatsapp_usage_platform_wide()` that predates this mission

The RPC (created in the commercial-packaging release, `20260904210400`) had **zero `is_test_fixture` exclusion** — confirmed by reading its SQL body directly. It was missed by the M-2 remediation pass (`20260903140100`) specifically because it had no frontend call site at the time, so nothing surfaced the gap. Since this mission is the first to wire it into a real screen, and shipping it unfiltered would immediately reintroduce the exact fixture-leak class of bug M-2 fixed everywhere else (all 13 production clubs are currently test fixtures), the fix was made in the same migration that adds the frontend call site (`20260908160000_platform_owner_v1_phase8_whatsapp_usage_fixture_filter.sql`), rather than shipping a new screen with a known-bad data source and filing it as a separate follow-up. This is a bug fix, not a product decision, but is flagged here since it touches an RPC this mission didn't originally author.

## 8. Phase 7: chose a single new RPC (`get_platform_attention_items`) over client-side composition

The mission allowed either approach and asked for justification. Chose the RPC because: (a) it matches this codebase's own established convention for exactly this shape of problem — every existing platform-wide aggregate (`get_platform_clubs_access`, `get_platform_whatsapp_health`, `get_commercial_usage`) is already a single batched, authorized RPC, not N client queries; (b) composing 9 independent per-tenant conditions client-side would mean up to 9 separate round trips on every Overview page load, reintroducing the exact N-round-trip anti-pattern Phase A already fixed once on this same page (`get_platform_clubs_access` replacing a per-club `Promise.all` loop); (c) "one row per (club, problem)" unioned across structurally different source tables (`whatsapp_accounts`, `notification_queue`, `clubs`, `platform_subscriptions`, `commercial_upgrade_requests`, `commercial_entitlements_usage`) is naturally a SQL `UNION ALL`, not an easy or reliable client-side merge.

## 9. Phase 7: which conditions to include, and which to explicitly skip

Per the mission's "do not invent unreliable signals" instruction, each of the 4 new conditions was checked against real, existing, reliable data before being added:
- **Included** (backed by real, already-relied-upon columns): trial/subscription ending soon (mirrors the existing `isSubscriptionExpiringSoon()` threshold from `labels.ts`, 3d trial / 7d paid, reimplemented in SQL since a stored procedure cannot call a TypeScript helper — any future change to that threshold must be mirrored by hand in both places, same limitation the parallel Phase 6 agent's MRR migration independently documented for the same threshold), subscription expired-but-not-cancelled (a real, distinct `platform_subscriptions.end_at <= now()` state), over/near a commercial plan limit (queries the existing `commercial_entitlements_usage` view directly, 80% warning threshold matching this codebase's already-established billing-review convention).
- **Explicitly skipped**: "onboarding incomplete" — confirmed via schema read (`20260815180000_phase3d_onboarding.sql`) that neither `clubs` nor `platform_subscriptions` has any real onboarding-status/progress column; only `flagged_duplicate` exists and is already covered as its own condition. Fabricating a signal from unrelated columns would have been exactly the kind of invented condition the mission explicitly warned against, so this was skipped and reported rather than approximated.
- **"New leads" (`contact_requests`) intentionally left OUT of the per-tenant RPC**: confirmed via schema read that `contact_requests` has no `club_id` column at all (an anonymous, pre-signup, insert-only inbox — its own table comment says "not a CRM"). It cannot be expressed as a `(club, problem)` row, so it remains its own small platform-wide card next to the Attention Center list rather than being forced into a per-tenant shape it doesn't have.

## 10. Phase 7: severity is a fixed 2-level ordering (danger/warning), not a score

Per the mission's explicit "not a complicated scoring engine yet" instruction, each of the 9 conditions is independently evaluated and tagged `danger` or `warning` (a simple, fixed classification, not a weighted composite). The list is sorted danger-first, then by recency — no single "health score" is computed or implied. This is consistent with, but structurally separate from, the parallel Phase 10 agent's `get_platform_tenant_health()` (HEALTHY/WATCH/AT_RISK) landed during this same mission window — the two were not merged into one signal here, since the mission scoped this phase narrowly to a per-tenant exception *list*, not a tenant health *classification*. Whether the Attention Center and Tenant Health should eventually be unified into one view is a real follow-up question, not decided here.

# Platform Owner Control Plane V1 — Phases 6+10 (Commercial Snapshot + Tenant Health)

Generated 2026-09-08, branch `feature/platform-owner-control-plane-v1`. Genuinely ambiguous product-judgment calls and hard data-model limitations found while implementing Phase 6 (Commercial Snapshot V1, `get_platform_commercial_snapshot()`) and Phase 10 (Tenant Health V1, `get_platform_tenant_health()`). Nothing below blocked shipping the parts that are confidently correct — each limitation was implemented as an explicit null/documented gap rather than a guess, per the mission's own "do not fake it" instruction.

## 11. Phase 6: trial → paid conversion rate is NOT implemented — returns null, not an estimate

Verified directly against every write path that can create a `platform_subscriptions` row (`create_platform_subscription`, `renew_platform_subscription`, `change_platform_plan`, `cancel_platform_subscription`): a trial-to-paid conversion is two fully independent manual Platform Owner actions with **no structural link** between the two rows. `previous_subscription_id` is populated only by `renew_platform_subscription()`/`change_platform_plan()`, both of which operate on an already-paid row — `create_platform_subscription()` itself never sets it, so a paid row created right after a trial carries no link back to that trial row. The only available fallback (same `club_id`, paid `start_at` shortly after trial `end_at`/`cancelled_at`) is a heuristic, not a real link, and would misclassify a club that re-trials or whose trial was cancelled for an unrelated reason (fraud, duplicate signup) and later paid independently. `get_platform_commercial_snapshot()` returns `trial_to_paid_conversion_rate = null` and `trial_to_paid_conversion_rate_unavailable = true` always, and the frontend renders an explicit "not yet available" note rather than a fabricated percentage. **Decision needed if you want this metric for real**: `create_platform_subscription()` would need a new optional parameter (e.g. `p_converted_from_trial_id uuid`) so the Platform Owner explicitly declares the link at the moment of conversion — a schema/RPC change, not something this migration should add unilaterally without your sign-off on the UX (should it be mandatory? optional? auto-suggested from the same club's most recent cancelled trial?).

## 12. Phase 6: MRR excludes founding-offer discount from `price_snapshot`, uses `founding_customer_slots` instead — confirm this is the intended commercial semantics

Found via direct schema read (not assumed): `price_snapshot` on a `paid` `platform_subscriptions` row is **always the full list price**, for every write path, including a founder's first paid subscription. The founding-offer 50%-off discount is applied entirely as a separate, read-time-only computation in `founding_customer_slots`/`get_founding_offer_status()` (`promotional_price` while `now() < promotion_end`, else `normal_price_after_promotion`) — it never touches `price_snapshot` or the invoice amount. MRR in `get_platform_commercial_snapshot()` therefore overrides `price_snapshot` with `founding_customer_slots`' dynamic current-effective-price for founder clubs. This is the mathematically correct reading of "MRR should represent normalized recurring subscription revenue, not cash collected" — but it does mean MRR and the per-club invoiced/collected amount (`platform_invoices.amount`, `get_platform_revenue_report()`) will legitimately disagree for any founder club during their promo window (MRR shows the discounted rate, invoices/collected revenue show the full list-price amount actually invoiced and collected). This divergence is real and intentional, not a bug — flagging it here so it isn't mistaken for a reconciliation defect later, and so you can confirm this is the commercial semantics you want (the alternative — MRR always equal to `price_snapshot` — would overstate founder-club revenue by 2x during their promo window, which seemed clearly wrong, but the resulting MRR/collected-revenue gap for founders is worth being aware of explicitly).

## 13. Phase 10: last-activity threshold (30 days) is a reasoned default, not derived from real usage data

The mission's own example question — "should a club with zero real activity ever since trial start be AT_RISK, or is that just a brand-new signup that hasn't had time yet?" — was resolved conservatively: a club is only flagged (WATCH-tier `activity_stale`/`activity_never_recorded`, never AT_RISK on its own) if it is **more than 30 days old** (`clubs.created_at`) **and** has zero recorded activity (MAX of `bookings.created_at`/`payments.received_at`/`attendance.marked_at`, same definition as the parallel Phase 4/5 agent's `get_platform_club_last_activity()`) in the trailing 30 days. A club still in its first 30 days is never flagged for this reason, so a legitimate new signup isn't penalized for not having activity yet. The 30-day number itself was chosen because it matches this schema's own "about a month" grace-window convention (`controlled_resource_grace_days` default, `platform_settings.default_grace_period_days`) — it is **not** derived from any actual distribution of real tenant activity (there are zero real paying customers today per the deep dive, so no such data exists to derive it from). **Decision needed**: confirm 30 days is the right window once real tenants exist, or adjust it — this is exactly the kind of business-judgment call the mission said should not be guessed permanently.

## 14. Phase 10: tenant health badge added to `PlatformClubsPage.tsx` only, NOT to Tenant 360 (`PlatformClubDetailPage.tsx`)

The mission explicitly allowed deferring Tenant 360 integration if editing that file concurrently was judged too risky. Confirmed via live `git status` during this mission that a parallel agent was actively modifying `PlatformClubDetailPage.tsx` (Tenant 360 / Last-Activity work) throughout this session, so the health badge was deliberately scoped to `PlatformClubsPage.tsx`'s list column only, per the mission's own fallback instruction, rather than risk a concurrent-edit collision on a 2000+-line file. `get_platform_tenant_health()` is a standalone, already-shipped RPC — adding the same badge (with its `reasons` array) to Tenant 360 is a small, low-risk follow-up once that page's concurrent work has landed and can be reviewed fresh.

# Platform Owner Control Plane V1 — Phase 15 Independent Security Review Findings

Generated 2026-09-08, branch `feature/platform-owner-control-plane-v1`, HEAD `a2d4396`. Reviewed by a fresh independent security-reviewer agent (did not implement any Control Plane V1 code). Full verdict: **no P0 or P1 findings** — the core claim (that `isPlatformOwner` is byte-for-byte unchanged and `isPlatformStaff` is a strictly additive, server-verified widening with no forgeable client-side trust) was verified true by direct diff and RPC read. ## 15. P2 — Pre-existing nav-vs-RPC authorization mismatch on 3-4 staff-facing screens

`get_platform_club_owners`, `get_platform_audit_log`, `get_platform_club_360`, and `get_platform_attention_items` are all gated `is_platform_owner()` only (no `has_platform_permission()` branch) — confirmed **pre-existing**, not introduced by this branch (same check existed before Phase 1, in `20260819150000`/`20260819100002`). Phase 1's nav-permission work now lets platform staff *see* the Owners/Audit/Tenant-360-detail/Attention-Center nav items (their `requiredPermissions` are narrower, e.g. `platform.club.view`/`platform.audit.view`), but the underlying RPCs still reject anyone who isn't the literal platform owner. Result: a legitimate staff member (e.g. `platform_support`) can click into these screens and gets a hard "not authorized" error — **fail-closed, not a leak**, but the staff-access feature doesn't functionally work end-to-end on these specific screens yet. Fix (when prioritized): extend these 4 RPCs' authorization check to `is_platform_owner() OR has_platform_permission(<appropriate key>)`, matching the pattern already used correctly in the new `get_platform_commercial_snapshot()`/`get_platform_tenant_health()` RPCs built this same mission.

## 16. P2 — `p_reason` on staff deactivate/role-change is optional at the RPC layer

`deactivate_platform_staff`/`set_platform_staff_role` (`20260908150000_platform_staff_actions_require_reason.sql`) accept `p_reason text default null` — the UI (`PlatformStaffPage.tsx`) disables Save until a reason is typed, but a direct RPC call (devtools, or curl with a valid staff JWT) can bypass this and deactivate/reassign a role with `p_reason: null`. This degrades **auditability** (the "why" is missing from that one audit row) but not **access control** — the action itself is still fully authorized-gated, and `audit_logs` remains hash-chained/immutable, so the action is still fully traceable, just without a stated reason. Acceptable as shipped; a stricter fix (making the parameter genuinely `not null` at the SQL layer, with a clear error surfaced to any non-UI caller) is a reasonable low-effort follow-up, not a blocker.
